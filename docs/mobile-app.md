# Застосунок «Мій підручник» (Flutter) — план

> Статус: чернетка плану, 23.11.2026. Коду застосунку ще немає.
> Цей документ — про **мобільний застосунок** для сайту https://my-pidruchnyk.github.io/ і про **API**, з якого застосунок бере дані.
> Усі цифри розмірів нижче виміряні на поточних даних репозиторію (`books.json`, `books/*/…`), а заголовки HTTP — на живому сайті.

## Коротко (на одну хвилину)

- **Що робимо першим:** Android-застосунок на Flutter, який читає ті самі підручники й тези, що й сайт, і **працює без інтернету** для завантажених книжок і вже переглянутих сторінок (дорога, укриття).
- **API = «статичний API»**: скрипт `tools/build_api.py` генерує в репозиторій папку `api/v1/` з маленькими JSON-маніфестами (каталог, книжка, сторінки з `sha256` і розмірами). Їх роздає той самий безкоштовний GitHub Pages. Картинки сторінок **не дублюються** — маніфест посилається на наявні `books/<slug>/pages/NNNN.webp`.
- **Завантаження книжки** = завантаження її сторінок по одній (≈100–310 файлів) за маніфестом, з перевіркою `sha256`, паралельно, з докачуванням після обриву. Окремі «архіви-пакети» — пізніше й лише якщо знадобиться.
- **Тести** — переносимо логіку `assets/quiz.js` у Dart (генерація на телефоні, працює офлайн), заздалегідь виправивши кілька вад генератора.
- **Сервер** (акаунти, синхронізація, вчитель бачить результати) — не в першій версії. Коли знадобиться — Supabase (безкоштовний тариф) з нормальною авторизацією; клієнтська перевірка «коду вчителя» в застосунок **не переноситься**.
- **Гроші:** Flutter і GitHub Pages — безкоштовно. Google Play — одноразово $25. App Store — $99 на рік. APK через GitHub Releases — безкоштовно.
- **Головний ризик — не технічний, а авторські права на підручники.** Перед публікацією в Google Play це треба вирішити (див. розділ 10).

## 1. Мета й межі MVP

### 1.1. Мета першої версії (Android, v1.0)

1. Встановити «Мій підручник» на телефон як звичайний застосунок (іконка, повноекранний режим, швидкий запуск).
2. Читати будь-який підручник: сторінка + тези цієї сторінки, як на сайті.
3. **Офлайн**: усе, що вже відкривали, і все, що явно завантажили, читається без мережі.
4. Керувати завантаженнями: бачити розмір, завантажити/поставити на паузу/видалити книжку, бачити зайняте місце.
5. Отримувати оновлення тез і сторінок без перевстановлення застосунку.

## 2. Архітектура застосунку

### 2.1. Принципи

- **Offline-first.** Екран завжди малюється з локальних даних (база + файли). Мережа лише **оновлює** локальні дані у фоні. Немає мережі — застосунок не «ламається», а показує те, що є.
- **Жодного «8» у коді.** Клас — це просто поле `grade` у даних. Ключ книжки всюди — пара `(grade, slug)`, бо `algebra` буде і в 8, і в 9 класі. Шляхи на диску: `books/<grade>/<slug>/…`. Назва застосунку — «Мій підручник», ID пакета без цифри класу.
- **Вміст, який зараз «зашитий» у `assets/app.js`** (емодзі предметів `ICON`, знахідний відмінок `ACC` для «Продовжимо алгебру?», неонові кольори груп `NEON`), **переїжджає в дані** (`catalog.json`), щоб новий клас не вимагав оновлення застосунку.
- **Тонкі шари, без «архітектурної астронавтики».** Один розробник має розуміти весь код.

### 2.3. Навігація (go_router)

| Маршрут | Екран |
|---|---|
| `/` | Каталог (якщо класів > 1 — перемикач класу вгорі; зараз він просто не показується) |
| `/g/:grade/:slug/p/:page` | Читалка (`page` — номер файлу/PDF, як у сайті `#algebra.40`) |
| `/g/:grade/:slug/quiz?page=40` | Тест до сторінки |
| `/mistakes` | Банк помилок |
| `/storage` | Сховище й завантаження |

Пізніше можна відкривати посилання сайту в застосунку (App Links), але адреси сайту — у «хеші» (`#algebra.40`), а Android App Links зіставляють лише шлях. Тож для цього знадобляться адреси без `#` — це питання на потім.

### 2.4. Компонування читалки на телефоні

- **Вертикально (телефон):** сторінка на весь екран; тези — у висувній нижній панелі (тягнеш угору — тези, вниз — сторінка). Кнопки «Тези», «Тест», «⚠️ Помилка?» внизу.
- **Горизонтально / планшет:** як на сайті — сторінка зліва, тези справа.
- Картинка 1200×1778 px у пам'яті займає ≈8,5 МБ, тож тримаємо декодованими лише поточну та сусідні сторінки, а мініатюри зміст/каталогу декодуємо з `cacheWidth`.

### 3.2. Де і як зберігаємо на телефоні

```
<папка підтримки застосунку>/            (getApplicationSupportDirectory)
  content/
    v1/index.json                         останній отриманий index
    grades/8/catalog.json
    books/8/algebra/
      manifest.json                       маніфест цієї книжки
      theses.json                         тези (нормалізовані)
      pages/0001.webp … 0259.webp         картинки сторінок
  db/app.sqlite                           drift: стан файлів, прогрес, помилки
```

- Папка **підтримки** застосунку, а не системний кеш: Android може сам чистити кеш-папку, а завантажені для укриття книжки не мають зникати.
- **Одне сховище для двох режимів.** Сторінка, переглянута онлайн, і сторінка із завантаженої книжки лежать в одному місці. Різниця — у позначці в БД:
  - `lazy` — переглянута, може бути видалена при переповненні кешу (LRU — найдавніше відкриті першими);
  - `pinned` — книжка завантажена користувачем, автоматично **ніколи** не видаляється.
  Так немає дублікатів: якщо 40 сторінок алгебри вже переглянуто, «Завантажити алгебру» докачає лише решту 219.
- Таблиця `page_files` у БД (спрощено):

```sql
CREATE TABLE page_files (
  grade INTEGER, slug TEXT, n INTEGER,          -- n = номер файлу (0001.webp → 1)
  sha256 TEXT NOT NULL,                          -- очікуваний, з маніфесту
  size INTEGER NOT NULL,
  state TEXT NOT NULL,                           -- 'missing' | 'lazy' | 'pinned' | 'stale'
  local_sha256 TEXT,                             -- що реально лежить на диску
  last_access INTEGER,                           -- для LRU
  PRIMARY KEY (grade, slug, n)
);
```

### 3.3. Два способи потрапити в офлайн

**А. Ліниве кешування (автоматично).** Відкрив сторінку з мережею → картинка збережена (`lazy`). Додатково підвантажуємо **наступні 2 і попередню** сторінки, щоб гортання не чекало мережі. Ліміт кешу за замовчуванням 250 МБ (налаштовується: 100 / 250 / 500 МБ / 1 ГБ).

**Б. «Завантажити книжку» (явно).** Кнопка на картці предмета й у читалці: «Завантажити для офлайну · 29 МБ». Позначає всі сторінки книжки як `pinned` і ставить у чергу ті, яких ще немає.

Плюс дешева опція: **«Тези всіх предметів офлайн (≈1,5 МБ)»** — вмикається за замовчуванням після першого запуску на Wi-Fi. Тоді навіть без картинок можна повторювати конспект і проходити тести з будь-якого предмета.

### 3.4. Чому «по файлах», а не одним архівом на книжку

| | По файлах (обрано для MVP) | Архів-пакет на книжку (`.zip`) |
|---|---|---|
| Місце на GitHub Pages | 0 додатково | +603 МБ дублікатів → перевищення ліміту 1 ГБ на сайт |
| Докачування після обриву | Природне: вже перевірені файли не качаємо | Потрібен HTTP Range (GitHub Pages його підтримує — перевірено, відповідь `206`), але один битий байт = перекачати шматок/архів |
| Оновлення 3 сторінок із 259 | Качаємо 3 файли | Перекачати весь архів (або складні дельти) |
| Спільний кеш із лінивим читанням | Так | Ні, треба розпаковувати |
| Кількість запитів | ≈100–310 на книжку (≈4 155 на весь клас) | 1 |
| Швидкість | 4–6 паралельних з'єднань; ≈30–60 с на 30–50 МБ при 10 Мбіт/с | Трохи швидше на повільному пінгу |

WebP уже стиснутий, тож архів майже нічого не виграв би за розміром. Якщо колись знадобиться (наприклад, повільний пінг у користувачів), пакети можна покласти в **GitHub Releases** (файл до 2 ГБ, не рахується в ліміт сайту) — маніфест уже має місце для поля `packs` (розділ 4.4).

### 3.5. Хід завантаження книжки

1. Перевірити вільне місце: потрібно `розмір_відсутніх_сторінок + 50 МБ` запасу. Якщо мало — показати «Потрібно 29 МБ, вільно 18 МБ. Видалити кеш переглянутого (120 МБ)?». (Вільне місце на Android — через невеликий платформний виклик `StatFs` або пакет на кшталт `disk_space`.)
2. Якщо мобільний інтернет і в налаштуваннях «лише Wi-Fi» вимкнено — один раз спитати: «Завантажити 29 МБ через мобільний інтернет?».
3. Поставити в чергу `background_downloader` групу `book:8/algebra` з відсутніх/застарілих сторінок, 4–6 паралельно, 3 повтори з паузою.
4. Кожен файл качається у `NNNN.webp.part` → рахуємо sha256 (в ізоляті) → якщо збігається з маніфестом, перейменовуємо в `NNNN.webp` і оновлюємо рядок у БД **однією транзакцією**. Якщо ні — видаляємо `.part`, повтор; після 3 невдач — сторінка у статусі «помилка», книжка «Частково: 257/259 · Повторити».
5. Сповіщення з прогресом «Алгебра — 120/259» (дає пакет). Застосунок можна закрити — завантаження продовжиться.
6. **Після обриву** (закрили застосунок, зник інтернет, перезавантажили телефон): під час запуску звіряємо БД і диск («є `pinned`, але файлу немає або sha не той» → у чергу). Нічого вже перевіреного не качається повторно.
7. Пауза/Продовжити/Скасувати — на екрані «Сховище» і в сповіщенні.

```

Зайнято застосунком: 142 МБ   Вільно на телефоні: 11,8 ГБ

  Алгебра              ✓ Завантажено · 29 МБ          [Видалити]
```

- «Видалити» книжку прибирає картинки, але **лишає тези** (вони малі) і прогрес. Підтвердження: «Видалити 29 МБ сторінок «Алгебри»? Тези й закладки залишаться».
- Розміри беремо з маніфесту (точні байти), а не рахуємо по диску щоразу.

### 3.7. Цілісність

- Ланцюжок довіри: `index.json` (HTTPS) → містить `sha256` каталогу → каталог містить `sha256` маніфесту книжки → маніфест містить `sha256` і `size` кожної сторінки й тез.
- Перевіряємо `sha256` **кожного** файлу після завантаження. Битий файл ніколи не потрапляє в «готові».
- Раз на тиждень (або вручну «Перевірити файли») — фонова перевірка завантажених книжок (SHA-256 для 600 МБ на сучасному телефоні — секунди-десятки секунд).
- **Безпека шляхів:** `slug` і `grade` з мережі перед використанням як імен папок перевіряємо регуляркою `^[a-z0-9-]{1,40}$` і `^\d{1,2}$`. Інакше зламаний/підмінений маніфест міг би записати файл «не туди» (`../../`).

### 3.8. Оновлення вмісту на телефоні

- **Тези:** нова `sha256` у маніфесті → тихо завантажити новий `theses.json` (≈50–130 КБ стиснуто), перевірити, замінити атомарно. Показати ненав'язливо: «Оновлено тези: Фізика».
- **Сторінки:** для кожної сторінки порівнюємо `sha256` у новому маніфесті й у БД. Змінені позначаємо `stale`:
  - у **завантажених** книжках — докачуємо автоматично, якщо Wi-Fi і зміна < 5 МБ, інакше кнопка «Оновити (3 стор., 0,4 МБ)»;
  - у **кеші** переглянутого — просто видаляємо застарілі, перекачаються при відкритті.
  - Поки нова версія не докачалась, показуємо стару картинку (краще стара, ніж жодної).
- **Нова книжка / новий клас** у каталозі — бейдж «Нове» на картці.
- **Книжку прибрали з каталогу** (наприклад, на вимогу правовласника) — див. розділ 4.5 (`withdrawn`): застосунок прибирає її з каталогу і **видаляє** локальні копії. Це важливо для юридичної чистоти.

## 4. API v1 — повна специфіка

### 4.1. Вибір: «статичний API» на GitHub Pages

**Що це.** Не сервер, а набір JSON-файлів, які скрипт `tools/build_api.py` генерує з наявних даних і кладе в репозиторій у `api/v1/`. GitHub Pages віддає їх як звичайні файли через CDN (Fastly). Для застосунку це виглядає як API: `GET https://my-pidruchnyk.github.io/api/v1/index.json`.

**Чому так:**

| Критерій | Статичний API на Pages | Власний сервер / функції |
|---|---|---|
| Вартість | $0 (вже використовується) | Безкоштовні тарифи мають ліміти, «засинання», картку |
| Надійність | CDN, нічого «не падає» | Ще одна система, яку треба стерегти |
| Офлайн-сумісність | Ідеальна: файли легко кешувати й перевіряти | Те саме, але складніше |
| Що вміє | Лише **читання** однакових для всіх даних | Персональні дані, запис |

Весь вміст (каталог, тези, сторінки) однаковий для всіх користувачів і змінюється рідко → статичний API підходить ідеально. Сервер потрібен лише для **персональних** даних (розділ 6).

### 4.2. Що реально віддає GitHub Pages (перевірено 23.11.2026)

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8     (для .webp — image/webp)
Content-Encoding: gzip                              (для JSON; WebP не стискається)
Cache-Control: max-age=600                          (10 хвилин — змінити не можна)
ETag: W/"6b04401a-215a"                             (для картинок — без W/)
Last-Modified: Mon, 23 Nov 2026 13:31:06 GMT
Access-Control-Allow-Origin: *                      (CORS дозволено — згодиться для Web)
Accept-Ranges: bytes                                (Range-запити → 206, перевірено)
Via: 1.1 varnish / X-Cache: MISS|HIT                (CDN Fastly)
```

- `If-None-Match: <ETag>` → **304 Not Modified** (перевірено). Тобто «нічого не змінилось» коштує кількасот байтів.
- **Важливо:** ETag на GitHub Pages має вигляд `"<час-деплою>-<розмір>"`, а `Last-Modified` у **всіх** файлів дорівнює часу останнього деплою. Тобто після **будь-якого** коміту (навіть зміни CSS) ETag зміниться у всіх файлів, хоча вміст той самий. Висновок: **ETag використовуємо лише для дешевого опитування маленьких JSON**, а рішення «чи змінився файл» приймаємо **тільки за `sha256` з маніфесту**.
- `max-age=600`: після деплою CDN може до 10 хвилин віддавати стару версію файлу. Щоб нова картинка сторінки не «застрягла», URL сторінки містить хвіст `?v=<перші 8 символів sha256>`: GitHub Pages параметр ігнорує (віддає той самий файл), але для кешу CDN і телефону це **новий** адрес.
- Власних заголовків (наприклад, `immutable`) на GitHub Pages поставити не можна — і не потрібно: кеш картинок застосунок веде сам.

### 4.3. Файли API

```
https://my-pidruchnyk.github.io/
  api/v1/index.json                               ← точка входу (≈1–2 КБ)
  api/v1/grades/8/catalog.json                    ← каталог класу (≈10 КБ)
  api/v1/grades/8/books/<slug>/manifest.json      ← маніфест книжки (≈25–35 КБ, gzip ≈15 КБ)
  api/v1/grades/8/books/<slug>/theses.json        ← нормалізовані тези (копія, ≈100–530 КБ, gzip ×4 менше)
  api/v1/grades/8/books/<slug>/cover.webp         ← мініатюра обкладинки 300 px (≈15 КБ), необов'язково
  api/v1/changelog.json                           ← «що нового» для людей
  books/<slug>/pages/NNNN.webp                    ← НАЯВНІ картинки (не копіюються)
  books/<slug>/text.json                          ← НАЯВНИЙ текст сторінок (за потреби)
```

Чому тези **копіюємо** в `api/v1/`, а сторінки — ні: тези малі (6,4 МБ разом), а копія дає **стабільний контракт** — сайт може змінювати формат `books/<slug>/theses.json` як завгодно, застосунок це не зачепить. Сторінки (603 МБ) копіювати не можна через ліміт 1 ГБ на сайт.

- `status`: `ready` | `coming` (показати «Скоро») | `withdrawn` (прибрати й видалити локально).
- `page_offset: null` (або відсутнє) — номери сторінок = номери файлів; `page_scale: 2` — PDF з розворотів (географія). Формула та сама, що `label()` у `assets/app.js`:

```dart
String label(Book b, int i) {
  if (b.pageOffset == null) return '$i';
  final s = b.pageScale ?? 1, p = s * i - b.pageOffset!;
  if (p < 1) return '';                 // обкладинка, форзац — без номера
  return s == 2 ? '$p–${p + 1}' : '$p'; // «78–79» для розворотів
}
int fromLabel(Book b, int x) =>
    b.pageOffset == null ? x : ((x + b.pageOffset!) / (b.pageScale ?? 1)).floor();
```

- `bytes.pages` — точна сума, щоб показати «Завантажити · 29 МБ» без маніфесту.
- `subject_acc`, `icon`, `accent` груп — дані, що зараз зашиті в `assets/app.js` (`ACC`, `ICON`, `NEON`).

- `pages` — компактні трійки `[n, sha256, size]` (у прикладі — справжні значення з репозиторію). URL сторінки: `content_base` + `page_url` з підстановкою `{n4}` = `0001`, `{sha8}` = перші 8 символів sha.

### 4.5. Версіонування й сумісність

- Шлях `api/v1/` — **мажорна** версія. У межах v1 дозволено лише **додавати** поля. Застосунок **ігнорує невідомі поля** й не падає від нових значень `kind`/`status`.
- Ламна зміна (перейменування, зміна типу поля) → нова папка `api/v2/`. `api/v1/` продовжуємо генерувати **щонайменше 12 місяців** (скрипт будує обидві).
- `schema` у кожному файлі — мінорний номер формату всередині v1, для діагностики.
- `app.min_supported_version` — «аварійний вимикач»: якщо стара версія застосунку не вміє нові дані, вона показує «Онови застосунок». **Але офлайн-читання вже завантаженого ніколи не блокуємо.**
- Прибирання книжки: спочатку `status: "withdrawn"` (місяць, щоб усі телефони дізнались і видалили копії), потім — видалити із каталогу.

### 4.6. Коли й що запитує застосунок

| Подія | Запити | Що відбувається |
|---|---|---|

Трафік «перевірки, що нічого не змінилось»: один `index.json` ≈1 КБ (304 — ще менше). Навіть 10 000 користувачів × 4 перевірки на день ≈ 40 МБ/день — дрібниця.

### 4.7. Як оновлення доходять від автора до телефону

```
Власник оновлює тези / сторінки → git push у main
   ↓
GitHub Action «build-api»: python tools/build_api.py → коміт api/v1/** (якщо щось змінилось)
   ↓
GitHub Pages деплой (≈1–2 хв) → CDN Fastly (до 10 хв старий кеш, max-age=600)
   ↓
Телефон: під час запуску/повернення (не частіше, ніж раз на 6 год) → index.json → … → дельта
   ↓
Тези — тихо; сторінки завантажених книжок — автоматично на Wi-Fi (< 5 МБ) або кнопкою
```

Середня затримка «від коміту до телефону»: від 15 хв до кількох годин — для підручника цього досить.

### 4.8. Скрипт `tools/build_api.py` (опис, не реалізація)

**Вхід:** `books.json`, `books/<slug>/theses.json`, `books/<slug>/text.json`, `books/<slug>/pages/*.webp`, плюс невеликий ручний файл `tools/api_meta.json` (або нові поля прямо в `books.json`, сайт їх ігноруватиме): `icon`, `subject_acc`, акценти груп, `app.latest_version`, `app.min_supported_version`, `notice`, список класів і їхніх `content_base`.

**Кроки:**

1. **Перевірка даних** (падає з помилкою, якщо щось не так):
   - для кожного `slug` є файли `0001.webp … NNNN.webp` рівно для `pages` з `books.json`, без пропусків і зайвих;
   - кожна картинка — коректний WebP 1200×1778 (через Pillow; інший розмір — попередження);
   - ключі `theses.pages` ⊆ `1..pages`; `kind` відомий; `points` — масив рядків; `terms` — `{term, def}`;
   - `slug` відповідає `^[a-z0-9-]+$`.
2. **Хеші:** sha256 і розмір кожного файлу. Кеш хешів `tools/.hash-cache.json` за `(шлях, розмір, mtime)`, щоб не рахувати 603 МБ щоразу (хоча і повний перерахунок — секунди).
3. **Нормалізація тез** → `api/v1/grades/<g>/books/<slug>/theses.json` (мініфікований JSON, `ensure_ascii=False`, сортовані ключі сторінок).
4. **Зміст `toc`** із заголовків `§ N` (сусідні сторінки з тим самим `§` об'єднуються в діапазон).
5. **Обкладинки** `cover.webp` 300 px з `0001.webp` (Pillow).
6. **Маніфести → каталог → index**, кожен з `sha256` дочірніх файлів.
7. **Детермінованість:** однакові дані → байт-у-байт однакові файли (сортування, фіксовані роздільники, `generated` не входить у хеш). Інакше кожен запуск «оновлював би» всі телефони.
8. Режим `--check` для CI: нічого не пише, падає, якщо `api/` застарів.

**Де запускати:**
- локально перед комітом (`python tools/build_api.py`), **або**
- GitHub Action `.github/workflows/build-api.yml` на `push` у `main` зі змінами `books/**`, `books.json`, `tools/**`: запускає скрипт і комітить `api/` від імені бота (`permissions: contents: write`). Безкоштовно (публічний репозиторій — необмежені хвилини Actions; приватний — 2 000 хв/міс на безкоштовному тарифі).
- `.nojekyll` у корені вже є — GitHub Pages віддасть `api/` як є.

Розмір `api/v1/` ≈7–8 МБ (переважно копії тез) — у ліміт сайту вкладається.

## 5. Логіка тестів: порт у Dart чи готові банки питань

### 5.1. Як зараз

`assets/quiz.js` на льоту з тез складає 12 питань: відповідність термінів (1-А, 2-Б, 3-В), відкрита відповідь одним словом, «визначення → термін», «чи правильне твердження», формули, «термін → визначення», «оберіть правильний факт». Варіанти-«дистрактори» беруться з тез **сусідніх сторінок** тієї ж книжки (пул сортується за відстанню від поточної сторінки). Тест за діапазоном параграфів шукає `§ N` у заголовках. Банк помилок — `localStorage p8:mistakes`, ключ `предмет|текст питання|правильна відповідь`, правильна відповідь у режимі банку прибирає запис.

### 5.2. Порівняння

| | **Порт генератора в Dart** (рекомендовано) | Готові банки питань в API |
|---|---|---|
| Офлайн | Так — тези вже на телефоні | Так, але треба качати банки |
| Різноманіття | Щоразу новий набір і порядок | Фіксований набір (або багато варіантів → великі файли: 4 155 сторінок × 12 питань × кілька варіантів) |
| Розмір даних | 0 додатково | Від кількох до десятків МБ |
| Узгодженість із сайтом | Треба підтримувати дві реалізації | Одна генерація (Python) для всіх |
| Якість | Залежить від евристик | Можна вручну перевіряти/редагувати |
| «Секретність» відповідей | Немає (як і зараз на сайті) | Теж немає — файли публічні |

**Рекомендація: перенести генератор у Dart** як окремий чистий пакет `quiz_engine` (без Flutter, лише Dart — легко тестувати й потім перевикористати на desktop/web). А поле `tests` у тезах залишити як **необов'язкове доповнення**: для сторінок, де власник захоче вручну перевірені питання, генератор їх використає (так уже працює `quiz.js`).

### 5.3. Як не розійтися із сайтом

1. У `quiz.js` замінити `Math.random()` на функцію `rng`, що передається параметром (наприклад, простий генератор mulberry32 із «зерном»). Поведінка сайту не зміниться.
2. У Dart реалізувати той самий mulberry32 і той самий порядок кроків.
3. Скрипт `tools/quiz_fixtures.js` (Node) генерує для 30–50 сторінок різних книжок тести з фіксованими зернами → JSON-«еталони».
4. Тест у Flutter (`quiz_engine_golden_test.dart`) перевіряє, що Dart видає **байт-у-байт те саме**. Зміна в одній реалізації без іншої — червоний тест.

### 5.4. Що варто виправити в генераторі ДО портування

Знайдено під час читання `quiz.js` і **виправлено на сайті у v15.9** — портувати вже виправлену версію:

- ✅ **«Чи правильне твердження…»**: раніше правильна відповідь завжди перша і твердження завжди правдиве. Тепер варіанти перемішуються, а ~50% тверджень хибні (`falsify()`: у реченні з тез підмінюється термін іншим терміном тієї ж книжки або змінюється число; якщо хибне скласти не можна — речення пропускається, щоб зберегти баланс). Службові рядки тез («Впр. 7…», «№ 1 — …») не стають питаннями.
- ✅ **Запасні «загальні» терміни** («Величина», «Енергія»…) більше не стають питаннями — лише неправильними варіантами, коли своїх замало.
- ✅ **Формули**: ключ проти дублів містить саму формулу — у тест потрапляють усі формули теми.
- ✅ **Склад тесту**: раніше всі 12 питань були «Який термін означає…», переважно з інших сторінок. Тепер спершу матеріал цієї сторінки/діапазону, типи чергуються по колу (термін, так/ні, формула, термін→визначення, факт), добір з решти книжки — лише до 12.
- ✅ **Відкрита відповідь**: однаковими вважаються різні апострофи (’ ' ʼ), ігноруються крапка/пробіли в кінці.

Для Dart-порту: `falsify()` і порядок по колу використовують `Math.random()` — у порті замінити на генератор із «зерном» (див. 5.3), щоб еталонні тести збігалися.

### 5.5. Банк помилок у застосунку

Таблиця `mistakes` у drift із тими самими полями, що й у `p8:mistakes` (`key`, предмет, питання, `wrongCount`, `addedAt`, `lastWrongAt`) + `grade`, `slug`, `page`, `updated_at`, `deleted_at` (для майбутньої синхронізації). Імпорт із сайту неможливий напряму (інше сховище) — з'явиться разом з акаунтами.

## 6. Майбутній динамічний бекенд

### 6.1. Навіщо (і лише для цього)

- Вхід (акаунт) → синхронізація банку помилок, останніх сторінок, закладок між телефоном, планшетом і сайтом.
- Кабінет учителя: клас, учні, видані СР/КР, результати.
- Вчитель отримує ключі відповідей **справді захищено**.

### 6.2. Безкоштовні варіанти (ліміти змінюються — звірити перед стартом)

| | **Supabase Free** | **Firebase Spark** | **Cloudflare Workers + D1** |
|---|---|---|---|
| БД | Postgres 500 МБ | Firestore 1 ГіБ; 50 тис. читань / 20 тис. записів **на добу** | D1 (SQLite) 5 ГБ; 5 млн читань рядків / 100 тис. записів на добу |
| Авторизація | Вбудована: e-mail, magic link, Google, Apple, анонімна; 50 тис. активних/міс | Вбудована (Firebase Auth) | **Немає** — писати самому або сторонній сервіс |
| Правила доступу | Row Level Security у Postgres | Security Rules | Код вручну |
| Серверний код | Edge Functions (500 тис. викликів/міс) | Cloud Functions — **лише на Blaze** (з карткою) | Workers: 100 тис. запитів/добу |
| Трафік | 5 ГБ/міс | 10 ГіБ/міс | Без плати за трафік |
| Підводні камені | Проєкт **«засинає» після 7 днів без запитів** (будиться вручну); 2 проєкти | Добові ліміти можуть «впертись» у час контрольних; прив'язка до Google | Багато ручної роботи з безпекою |
| Flutter SDK | `supabase_flutter` (офіційний) | `firebase_*` (офіційні) | Немає (звичайний HTTP) |

**Рекомендація: Supabase** — SQL і зрозумілі зв'язки «вчитель — клас — учень — результат», готовий вхід, правила доступу на рівні БД, без картки. «Засинання» не проблема, коли є щоденні користувачі; якщо проєкт стане важливим — Pro-тариф ($25/міс) або перенесення (Postgres легко експортувати).
**Cloudflare R2** (10 ГБ, трафік безкоштовний) — окремо, як дзеркало **вмісту**, якщо закінчиться трафік GitHub Pages (розділ 10.2).

### 6.3. Модель даних (ескіз, Postgres)

```sql
profiles      (id uuid PK = auth.users.id, role text CHECK (role IN ('student','teacher','admin')),
               display_name text, created_at timestamptz)
progress      (user_id, grade int, slug text, last_page int, updated_at, PK(user_id, grade, slug))
bookmarks     (id, user_id, grade, slug, page, note text, created_at, deleted_at)
mistakes      (user_id, key text, grade, slug, page, subject, question jsonb,
               wrong_count int, added_at, last_wrong_at, updated_at, deleted_at, PK(user_id, key))
classes       (id, teacher_id → profiles, title, join_code text UNIQUE, created_at)
class_members (class_id, student_id, joined_at, PK(class_id, student_id))
assignments   (id, class_id, kind text ('test','sr','kr','exam'), title, spec jsonb,
               questions jsonb,          -- БЕЗ правильних відповідей (бачать учні)
               opens_at, due_at, created_at)
assignment_keys (assignment_id PK, answers jsonb)   -- лише вчитель цього класу (RLS)
attempts      (id, assignment_id, student_id, answers jsonb, score numeric,
               started_at, submitted_at)
```

- **Синхронізація** «спочатку локально»: телефон працює з drift як зараз, а в мережі відправляє зміни з `updated_at > last_sync` і забирає чужі; конфлікт — «перемагає новіший `updated_at`»; видалення — через `deleted_at` (щоб не «воскресали»).
- **Оцінювання** — серверна функція `submit_attempt(assignment_id, answers)`: порівнює з `assignment_keys` і записує бал. Учень **ніколи** не отримує ключ.

### 6.4. Безпека

- **Клієнтський «код учителя» (перевірка SHA-256 у браузері) у застосунок не переносимо.** APK розпаковується за хвилину; будь-який код/хеш у ньому — публічний. Те саме, до речі, стосується і сайту — це лише «замок від чесних».
- Роль `teacher` видає **адміністратор** (власник) після перевірки (наприклад, заявка + ручне підтвердження), а не «хто знає пароль».
- Чесне застереження: поки тести генеруються з **публічних** тез на пристрої, будь-хто може згенерувати такий самий тест і побачити відповіді. Справжня закритість — лише коли вчитель створює варіант **на сервері** (або завантажує його туди), а ключ лежить у `assignment_keys` під RLS.
- У застосунку немає секретів: ключ `anon` Supabase публічний за задумом, безпека — у RLS-правилах. Токен Telegram-бота **ніколи** не потрапляє в застосунок.
- Діти (13–14 років): мінімум персональних даних (без справжнього імені, без телефону), можливість анонімного входу, видалення акаунта з застосунку (вимога Google Play), зрозуміла політика конфіденційності.

## 10. Ризики

### 10.1. Авторські права на підручники — головний ризик

- `README.md` сайту чесно каже: підручники — електронні версії видань МОН, права належать авторам і видавництвам. **Те, що МОН безкоштовно викладає PDF, не означає дозволу їх розповсюджувати в іншому застосунку.**
- Google Play (політика «Інтелектуальна власність») і App Store (правило 5.2) вимагають, щоб у розробника були **права** на вміст. Скарга правовласника → видалення застосунку; повторні порушення → **блокування акаунта розробника** (і $25 пропадуть, і новий акаунт важко отримати).
- Тези — похідний твір (переказ), а тести побудовані з тез; це менший, але теж не нульовий ризик.

Що перевірити / зробити (це не юридична консультація; бажано порадитися з юристом з авторського права):

1. На якій **ліцензії/умовах** МОН/ІМЗО (lib.imzo.gov.ua тощо) публікує ці PDF; чи дозволено некомерційне розповсюдження в незмінному вигляді.
2. Написати **видавництвам** (зазначені на обкладинках: «Генеза» та інші) і, за можливості, МОН з проханням дозволу на некомерційне освітнє використання; зберегти відповіді — App Store може попросити документи.
3. Заздалегідь мати **план Б**: варіант застосунку без картинок сторінок (тільки тези, тести й посилання «Відкрити офіційний PDF»), який можна випустити, якщо дозволу немає.
4. Механізм швидкого прибирання книжки — `status: "withdrawn"` (розділ 4.5) — закладено.
5. У застосунку: сторінка «Про застосунок» з указанням правовласників, контакт для скарг, «некомерційний освітній проєкт», жодної реклами й платежів.

Поки (1)–(2) не з'ясовано, **розумно почати з APK через GitHub Releases і закритого тестування**, а в відкритий Google Play виходити після відповіді правовласників.

### 10.2. Розмір даних і ліміти GitHub Pages

- Ліміти GitHub Pages: опублікований сайт **≤ 1 ГБ**; трафік — «м'який» ліміт **100 ГБ на місяць**; репозиторій бажано < 1 ГБ (зараз сам репозиторій ≈577 МБ у стиснутому вигляді, сайт ≈620 МБ).
- **Другий клас у тому ж репозиторії вже не вміститься в 1 ГБ.** Рішення, закладене в API: кожен клас — **окремий репозиторій і окремий сайт GitHub Pages** (наприклад, `my-pidruchnyk.github.io/grade-9/`), а `index.json` головного сайту вказує на його `content_base`. Кожен проєктний сайт має свій ліміт 1 ГБ. Безкоштовно.
- Трафік: 100 ГБ/міс ≈ 3 000 завантажень однієї книжки (у середньому 33 МБ) або ≈165 завантажень усього класу (603 МБ) — плюс трафік сайту. Якщо застосунок стане популярним, цього **не вистачить**. Запобіжники:
  - лінивий кеш + «завантажувати те, що треба», а не «все»; кнопку «Завантажити всі» ставимо з чесним попередженням про розмір;
  - стежити за трафіком (GitHub надсилає лист при перевищенні);
  - **дзеркало** у Cloudflare R2 (10 ГБ безкоштовно, **трафік безкоштовний**, 10 млн читань/міс) — поле `mirrors` в `index.json`, перемикання без оновлення застосунку;
  - пізніше — «економна якість» картинок (наприклад, 900 px), удвічі менша.
- Телефон: завантаження всього класу — 0,6 ГБ; на бюджетних телефонах це відчутно → чесний індикатор місця і ліміт кешу.

### 10.3. Безпека

- Лише HTTPS (Android: заборона незашифрованого трафіку — за замовчуванням).
- Перевірка `sha256` усього, що качається; перевірка `slug`/`grade` перед використанням у шляхах; ліміт розміру JSON (наприклад, 20 МБ) і картинки (5 МБ), щоб зламаний файл не «повісив» телефон.
- Жодних секретів у застосунку; клієнтський код учителя не переносимо (розділ 6.4).
- Посилання із «⚠️ Помилка?» відкриваються лише на `t.me` (білий список доменів).
- Збір даних: у MVP **жодної** аналітики й реклами → проста анкета «Безпека даних» у Play. Звіти про падіння — за бажанням (Sentry має безкоштовний тариф; Firebase Crashlytics — безкоштовний, але це SDK Google) — відкрите питання.

## 12. Відкриті питання

1. **Права на підручники.** Чи є (чи буде) дозвіл від видавництв/МОН? Якщо ні — випускати в Play «план Б» (лише тези й тести + посилання на офіційний PDF)?
2. **Канал першого релізу:** одразу Google Play (з 14-денним закритим тестуванням) чи спершу APK через GitHub Releases? Від цього залежить, яким ключем підписувати.
3. **ID застосунку й назва в магазині:** `io.github.mypidruchnyk` чи інший (наприклад, якщо буде власний домен)? Назва «Мій підручник» вільна в Play?
4. **Наступні класи** — окремі репозиторії/сайти GitHub Pages (рекомендовано через ліміт 1 ГБ) чи інший хостинг картинок (Cloudflare R2)?
5. **Код застосунку** — публічний репозиторій (безкоштовні хвилини Actions, можливий F-Droid) чи приватний, як конвеєр сайту?
6. **Тести в MVP** чи у v1.1? (Без них реліз швидший на ≈1,5 тижня.)
7. **Якість картинок:** чи достатньо 1200 px для дрібного шрифту при збільшенні? Чи потрібна «економна» версія для слабкого інтернету?
8. **Звіти про падіння:** збирати (Sentry/Crashlytics) чи взагалі нічого не збирати?
9. **Цільовий вік у Play:** «13+» чи з дітьми молодше 13 (тоді суворіша політика «Families»)?
10. **«Завантажити всі книжки»** — дозволяти одним натиском (603 МБ трафіку з ліміту GitHub Pages) чи лише по одній?
11. **Вади генератора тестів** (5.4) — виправляти й на сайті одночасно (рекомендовано), чи лише в застосунку?
12. **Хто вчитель** у майбутньому кабінеті: як власник перевірятиме заявки вчителів (ручне підтвердження, посилання на школу)?
